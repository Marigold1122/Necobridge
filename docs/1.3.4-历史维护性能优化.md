# 1.3.4 历史维护重复工作优化

本包包含此前尚未提交的1.3.1～1.3.3全部性能优化。此轮只改历史维护调度及保留清理算法，不改输入状态/右键/穿屏/界面外观。

## 本轮修改

- 原来分页、搜索、复制新记录前后都会扫描全库图片引用和所有副本目录；即使数据库根本没有删除记录也扫描。现在用一个“文件引用需清理”状态，只有删除/过期/容量回收、首次启动、显式清理或图片写入失败产生孤立文件时才扫描。
- 扫描完成后才复位状态；扫描失败保留待清理状态，下次维护仍会尝试，不假成功。
- 调低保留上限时，不再每删一条重新COUNT/SUM整个表。事务内统计一次，顺序读取最旧的非收藏、非保护项，确定所需删除记录后用复用命令删除。
- 收藏、日期、条数、字节限制、保护当前记录、事务回滚和原文件清理规则保留。启动和显式Prune仍会查孤立文件，不增加定时扫描。

## 优化前后对照

临时项目 `.tools/history-compare` 编译保留的优化前HistoryStore与当前源码，两者从同一个500条记录数据库复制得到，Release模式。使用临时目录，不读取真实历史数据。累计分配使用GC.GetTotalAllocatedBytes，包括工作线程；单次耗时仅参考。

|操作|优化前|优化后|
|---|---:|---:|
|无删除变化，连续200次读取第一页：分配|36,946,096字节|11,214,864字节|
|同上耗时|305.5ms|215.5ms|
|保留500降至50：分配|785,128字节|204,744字节|
|同上耗时|47.6ms|5.2ms|

两边最终保留记录ID及顺序完全相同。干净读取不扫描孤立文件；显式维护仍删除模拟孤立文件。现有HistorySmoke通过重启、图片、去重、搜索、收藏、保存副本删除、清空、日期/条数/容量和未完成副本恢复。

这些是历史操作的分配和耗时变化，不是静息进程内存下降约70%。没有停止或替换用户正在运行的进程，也没有执行强制GC/工作集裁剪。之前用户测到的55MB不作为此轮已测后的数字。

## 重新审查候选

网络消息改二进制、重新设计WPF宿主、改全局GC策略可能继续减小开销，但涉及兼容性/架构/手感，当前不为未知收益实施。四字节帧头等微小分配也没有引入复杂池管理。此轮以可复现的冗余维护工作为限。
