# 1.3.3 图片处理分配优化

包含1.3.1、1.3.2尚未提交的全部优化。本轮继续按“找出实际开销→判断是否过度→实施并对照”的方式检查。

## 本轮实施

### 图片指纹

原来解码PNG后另申请一份完整BGRA数组，只为了算SHA256。现在保留相同解码/标准化过程，按最多64KiB的像素条带顺序加入增量哈希。最终指纹完全相同，不改变去重、回环抑制或网络语义。条带使用后清零。

1920×1080、随机BGRA测试图，对照旧算法：托管分配8,305,656→65,360字节，减少约99.2%。这不包含原生解码器占用，也不是进程静息内存下降值。

### 图片剪贴板写入

保留PNG、Bitmap、DIBV5和传统DIB格式兼容性。直接将像素写入本来就需要的DIBV5目标数组，再从中生成传统DIB，不再保留第三份完整像素临时数组。1080p图片少一份8,294,400字节数组，4K图片少一份约31.6MiB数组；不能将不同阶段的节省简单相加成静息降幅。

## 对照检查

- 对1080p随机像素、alpha逐行对照，指纹与旧算法一致，DIBV5和传统DIB的字节及行方向不变。
- ClipboardSmoke已有的透明/半透明、不透明截图、原生格式兼容、图片传输和回环检查通过。使用模拟剪贴板和临时目标，不访问真实桌面剪贴板。
- PerformanceSmoke复核之前的连接查询、帧缓冲、缩略图、长文本、历史释放及延迟OLE构造，通过。
- 编译0警告0错误，发行包完整性另行核验。

## 再次检查后的边界

下列候选没有为了降低数字而实施：

- 删除Bitmap/DIB兼容格式：可能让浏览器、画图、聊天软件无法粘贴，属于功能退化。
- 全局换用自建延迟渲染COM剪贴板：增加复杂生命周期与退出失效风险，对当前目标过度。
- 重写WPF为纯托盘宿主或另一UI框架：属于架构迁移，不是低风险内存优化。
- 固定压低GC堆上限、强制GC、工作集裁剪：可能使频繁复制卡顿，只改变显示数字，未采用。
- 增加全局图片缓存：可能提高滚动命中率，但会抵消静息内存目标，当前保持可见范围加载。

因此当前这一轮以已测量、保留兼容性的优化收尾。用户反馈1.3.2静息约55MB是用户现场观测；本轮没有终止或替换该进程，尚不能宣称整进程再下降多少。
